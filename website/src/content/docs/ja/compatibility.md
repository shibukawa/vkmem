代役に対して通ったテストが何かを証明できるのは、代役が本物と同じように振る舞う範囲だけです。vkmemの場合、この問いは互換実装よりずっと狭くなります。すべてのコマンドはValkey 9.1.2自身のCのコードで実行されるからです。振る舞いが変わるのは、そのコードが土台に求めるものが欠けている場所だけです。スレッド、子プロセス、外向きの接続、そしておよそ2 GiBを超えるメモリです。

## Valkeyと同じように動くもの

以下は、テストスイートで動かしたか、動いているサーバーに対して確かめたものです。網羅した一覧ではありません。欠けている機能に頼らないコマンドは、どのValkeyサーバーでも動くのと同じコードで動きます。

- **データ型。** 文字列、ハッシュ、リスト、セット、ソート済みセット、ビットマップ、HyperLogLog、geo、コンシューマグループ付きのストリーム。
- **キー。** `EX`/`PX`による有効期限、`MATCH`付きの`KEYS`と`SCAN`、`DUMP`/`RESTORE`、`OBJECT`、`MEMORY USAGE`。
- **データベース。** 16個の論理データベース、`SELECT`、`SWAPDB`、`FLUSHALL`、`FLUSHDB`。
- **トランザクション。** `MULTI`/`EXEC`。
- **スクリプト。** `EVAL`、`SCRIPT LOAD`、Valkey Functions(`FUNCTION LOAD`、`FCALL`)、そして`cjson`などValkeyに同梱のLuaライブラリ。Luaは本物のエンジンを静的にリンクしています。
- **メッセージング。** `SUBSCRIBE`、`PSUBSCRIBE`、`PUBLISH`。
- **タイムアウト付きのブロッキングコマンド。** `BLPOP`、`BZPOPMIN`、`XREAD BLOCK`、`WAIT`は、ほかに通信のないサーバーでもタイムアウトで戻ります。
- **プロトコルと管理。** RESP2とRESP3(`HELLO 3`)、`AUTH`とACLユーザー、`CONFIG GET`/`SET`、`INFO`、`COMMAND`、`CLIENT`。`DEBUG`系のコマンドは`--enable-debug-command yes`を付ければ使えます。
- **メモリ上のスナップショット。** `SAVE`と`DEBUG RELOAD`は、vkmemのメモリ上のファイルシステムにRDBファイルを書き、読み戻します。Go、Python、Node.js、Javaの各アダプタも同じ仕組みを使い、データを一度だけ準備して分離されたサーバーを起動できます。コピーされるのはシリアライズされたキー空間で、接続やプロセスの状態ではありません。

Goのテストスイートはvalkey-goを使っています。ほかのクライアントも、同じサーバーのコードに同じプロトコルで話しかけます。

## 土台に欠けているために失敗するもの

| 機能 | どうなるか | 理由 |
|---|---|---|
| `BGSAVE`、`BGREWRITEAOF` | エラー応答 | どちらも子プロセスをforkするが、`fork`がない |
| 定期保存とAOF | vkmemは`save ""`と`appendonly no`で起動します。有効にするとメモリ上のファイルシステムに書かれ、それが引き起こすバックグラウンド保存は失敗します。`Close`のあとには何も残りません。 | `fork`もディスクもない |
| レプリケーション | `REPLICAOF`は受け付けますが、プライマリへの接続が拒否されるので、同期は始まりません | ホストが外向きの接続をしない |
| クラスタモード、Sentinel | `CLUSTER`系のコマンドは、クラスタ機能が無効だと応答します | この用途向けにはビルドしていない |
| TLS、RDMA | 使えません | コンパイルしていない |
| ロード可能モジュール | `MODULE LOAD`は既定で無効で、有効にしても読み込めません | 静的ビルドで、動的ローダーがない |
| I/Oスレッド | `io-threads`は1のまま。`INFO`は`io_threads_active:0`を報告します | スレッドがない |
| およそ2 GiBを超えるデータ | メモリ確保が失敗します | 32ビットのWebAssemblyで、確保するメモリが2 GiB |

## 値の見え方が違うもの

- `INFO server`は`arch_bits:32`と`multiplexing_api:select`を報告します。`INFO memory`の`total_system_memory`は、4 GiBのアドレス空間の大きさです。
- `maxmemory`を指定しなければ、Valkeyは32ビットのインスタンスだと判断して3 GBに設定し、ポリシーを`noeviction`にします。
- バックグラウンドジョブはその場で実行されます。`FLUSHALL`や`UNLINK`などの遅延解放は、ネイティブのサーバーならバックグラウンドのスレッドに任せる解放を、応答の前に済ませます。大きなキー空間をフラッシュすると応答までの時間は延びますが、応答のあとに解放が続くこともありません。
- `DEBUG SLEEP`や長いスクリプトが唯一のスレッドを塞ぐのは、Valkeyと同じです。

## 待ち受ける場所

vkmemは`127.0.0.1`とUnixドメインソケットで待ち受けます。マシンの外からは届かないので、`--protected-mode`は無効にしてあります。`WithArgs`、`args`、`-- ...`で渡した引数は、vkmemの既定値のあとで`valkey-server`に渡るので、既定値を上書きします。
