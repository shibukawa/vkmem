テストプロセスの中で動くサーバーが、コンテナより速く起動するのは予想どおりでしょう。気になるのは、動き始めてからです。変換したコードは、ネイティブの`valkey-server`と比べてどれだけ遅いのか。同じマシンで測ると、vkmemの起動は1.6ミリ秒で、最も速いコンテナの経路より約200倍速く、スループットはネイティブの`valkey-server`の72〜98%でした。以下の表が、それぞれの数字の出どころです。

## 計測条件

2026年9月15日に、Apple M3(8コア、16 GiB)、macOS 27.0、Go 1.27.0、OrbStack上のDocker 29.4.0、Testcontainers for Go 0.44.0、Devbox 0.17.5で計測しました。コンテナの経路はlinux/arm64の`valkey/valkey:9.1.2`を使います。DevboxがインストールするのはValkey 9.1.1で、当時のnixpkgsで最新のバージョンを、macOS向けにネイティブビルドしたものです。

どのサーバーも、テストスイートでの設定と同じく永続化を切って動かしました(`save ""`、`appendonly no`)。対象ごとに5回、毎回新しいプロセスで計測し、スループットは最初の3回で計測しています。表の値は中央値です。

マシンは空いていたわけではありません。デスクトップのプロセスがロードアベレージを8コアに対して4〜6に保ち、同じDockerのVMではアイドル状態のOpenSearchコンテナが2つ動いていました。10%程度までの差は、誤差と見てください。

| 経路 | 計測したもの |
|---|---|
| vkmem、プロセス内 | 計測しているGoのプロセスの中での`vkmem.Start()` |
| vkmem-server | Python、Node.js、Javaのパッケージが起動するバイナリを、子プロセスとして起動したもの |
| docker run | 永続化を切った`docker run -d --rm -p 127.0.0.1::6379 valkey/valkey:9.1.2` |
| Testcontainers | 同じイメージでの`testcontainers.Run`。「Ready to accept connections」を待つ。新しいプロセスではRyukも起動する |
| Devbox | valkeyプラグイン自身のサービスを`devbox services up -b`で起動したもの。プラグインの`valkey.conf`をincludeし、永続化を切る設定ファイルを生成して渡す |

## 起動と停止

| 経路 | PONGが返るまで | 範囲(n=5) | 停止 |
|---|---:|---:|---:|
| vkmem、プロセス内 | **1.6 ms** | 1.5〜11.3 ms | 0.6 ms |
| vkmem-server | **29 ms** | 29〜44 ms | 1.8 ms |
| docker run | **317 ms** | 153〜469 ms | 268 ms |
| Devbox | **434 ms** | 417〜497 ms | 282 ms |
| Testcontainers | **502 ms** | 452〜602 ms | 218 ms |

起動の計時は、起動の呼び出しから、新しいTCP接続が`PONG`を受け取るまでです。イメージのpullと`devbox install`は計時の前に済ませています。`vkmem-server`は計時の前に一度起動しておきました。macOSは新しく書き込まれた実行ファイルを初回起動時に検査し、ビルドごとに一度、約350ミリ秒かかるからです。停止はそれぞれ`Close()`、子プロセスの標準入力を閉じる操作、`docker stop`、`TerminateContainer`、`devbox services stop`です。

コンテナの行のコストを、テストスイートはテストプロセスかテストクラスにつき一度だけ払い、テストの間はキー空間をフラッシュして済ませます。vkmemはプロセス内なら起動と停止を合わせて約2ミリ秒です。これなら、テストの1つ1つに専用のサーバーを持たせられます。

## 往復

| 経路 | TCPでSET+GET | UnixソケットでSET+GET | EVAL(1行のスクリプト) | 10,000キーのFLUSHALL |
|---|---:|---:|---:|---:|
| vkmem、プロセス内 | 44 µs | 19 µs | 24 µs | 0.35 ms |
| vkmem-server | 47 µs | 22 µs | 26 µs | 0.36 ms |
| docker run | 129 µs | — | 77 µs | 0.09 ms |
| Testcontainers | 106 µs | — | 55 µs | 0.07 ms |
| Devbox(ネイティブの9.1.1) | 36 µs | 16 µs | 22 µs | 0.03 ms |

最小限の同期RESPクライアントが、1本の接続でコマンドを1つ送り、応答を待ちます。往復の値は、300回の暖機のあとの3,000回の中央値です。スクリプトは`return redis.call('GET', KEYS[1])`です。`FLUSHALL`は、64バイトの値を持つキーを10,000個入れてから計時し、5回の中央値を取りました。

- **エンジンのコストは約20%です。** ネイティブのサーバーはSET+GETにTCPで36 µs、ソケットで16 µsかかり、vkmemは44 µsと19 µsです。この差が、変換したコードとホストのソケット層の分です。
- **コンテナは、VMに入るネットワークの分を払います。** macOSでは、Dockerのポート転送が1往復ごとに70〜90 µsを足します。サーバー自身の処理時間より長い時間です。コンテナのUnixソケットには、ホストから届きません。
- **Unixソケットを使うと、vkmemの往復は半分以下になります。**
- **FLUSHALLだけは、vkmemのほうがコンテナより遅くなります。** vkmemはバックグラウンドジョブをその場で実行するので、10,000個のキーを解放し終えてから応答します。ネイティブのサーバーは先に応答し、解放はバックグラウンドのスレッドで行います。

## スループット

どの対象も、Devbox環境の`valkey-benchmark` 9.1.1で負荷をかけました。クライアントのバイナリはすべて同じです。各テストは50本の接続を使い、パイプラインなしで100,000リクエスト、1往復16コマンドのパイプラインで500,000リクエストを送りました。3回の中央値で、単位は1秒あたりのリクエスト数です。

**パイプラインなし**

| 経路 | SET | GET | LRANGE_100 |
|---|---:|---:|---:|
| vkmem、プロセス内、TCP | 161,031 | 159,744 | 95,969 |
| vkmem、プロセス内、Unixソケット | 346,021 | 338,983 | 127,877 |
| vkmem-server、TCP | 144,718 | 123,457 | 86,059 |
| vkmem-server、Unixソケット | 304,878 | 319,489 | 106,496 |
| docker run、TCP | 56,818 | 58,005 | 47,438 |
| Testcontainers、TCP | 66,711 | 75,758 | 65,531 |
| Devbox、TCP | 164,204 | 186,916 | 97,561 |
| Devbox、Unixソケット | 450,450 | 418,410 | 156,250 |

**1往復あたり16コマンド**

| 経路 | SET | GET |
|---|---:|---:|
| vkmem、プロセス内、TCP | 1,054,852 | 1,457,726 |
| vkmem、プロセス内、Unixソケット | 1,501,502 | 1,886,792 |
| vkmem-server、TCP | 1,234,568 | 1,243,781 |
| vkmem-server、Unixソケット | 1,259,446 | 1,533,742 |
| docker run、TCP | 540,541 | 643,501 |
| Testcontainers、TCP | 811,688 | 922,509 |
| Devbox、TCP | 1,199,041 | 1,639,344 |
| Devbox、Unixソケット | 1,901,141 | 2,617,801 |

ネットワークが支配的な、パイプラインなしのTCPでは、vkmemはSETとLRANGE_100でネイティブのサーバーとの差が2%以内、GETでは15%遅れます。サーバー自身の処理が支配的になると、つまりUnixソケットやパイプラインでは、ネイティブのサーバーが11〜28%先に出ます。コンテナの経路は、TCPでネイティブのサーバーの3分の1から3分の2の速さでした。プロセス内とvkmem-serverの行は同じコードを動かしていて、その差はこのマシンの誤差の範囲です。

## メモリ

| 経路 | 起動直後 | 負荷のあと | 補助プロセス | 計測方法 |
|---|---:|---:|---:|---|
| vkmem、プロセス内 | 3.2 MiB | 14.5 MiB | — | テストプロセスの`phys_footprint`の増分 |
| vkmem-server | 5.5 MiB | 19.0 MiB | — | 子プロセスの`phys_footprint` |
| docker run | 5.8 MiB | 8.8 MiB | — | `docker stats` |
| Testcontainers | 4.9 MiB | 7.8 MiB | Ryuk 9.5 MiB | `docker stats` |
| Devbox | 3.6 MiB | 7.3 MiB | process-compose 22.0 MiB | `phys_footprint` |

「負荷のあと」は、往復とフラッシュ、そして最初の3回ではスループットの計測を終えたあとの値です。vkmemのここが大きいのは、最大到達量だからです。WebAssemblyのメモリは縮まないので、ベンチマークの間にValkeyが触ったページは`Close`まで常駐メモリに残ります。計測方法も揃っていません。macOSの`phys_footprint`はプロセスの書き込み済みメモリを数えます。`docker stats`はページキャッシュを除いたコンテナのcgroupのメモリで、Dockerデーモンと、macOSでコンテナに必要なOrbStackのVMは含みません。どのサーバーも小さく、この差でテストの構成が決まることはないでしょう。

## ダウンロードとリンクのサイズ

| 最初の実行で入ってくるもの | サイズ |
|---|---:|
| Devbox: Valkey 9.1.1のNixクロージャ | ダウンロード4.5 MB、展開後10.5 MB |
| npmとJavaのパッケージに入るvkmem-server(gzip圧縮) | 4.7 MB、非圧縮で11.8 MB |
| Go: テストバイナリにリンクされるvkmem | strip済みで+9.7 MB、シンボル付きで+15.6 MB |
| linux/arm64の`valkey/valkey:9.1.2` | 圧縮で48.4 MB、ディスク上で144.8 MB |
| TestcontainersのRyukイメージ(Valkeyのイメージとは別に) | 圧縮で2.1 MB |

数えているのは、vkmemやValkeyを使う構成が追加するものだけです。Devbox自体のインストールとNix、そしてコンテナのランタイムは含みません。Goの行は、サーバーを1つ起動して止めるだけのstrip済みプログラムと、空のプログラムとの差です。Goのモジュールのソースそのものは約29 MBの生成コードで、一度コンパイルしたあとはビルドキャッシュから使われます。

## 再現する

```bash
cd bench/alternatives
RUNS=5 THROUGHPUT_RUNS=3 ./run.sh
```

計測ハーネスには、macOS(メモリを`footprint(1)`で取るため)、Docker、Devbox、Nixが必要です。生のサンプルは`results/raw.jsonl`、サイズは`results/sizes.json`、中央値は`results/summary.json`に書き出されます。`TARGETS="vkmem devbox" RUNS=1 ./run.sh`とすれば、一部の対象だけを計測します。
